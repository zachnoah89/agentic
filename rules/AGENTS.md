# Lab Security & Anti-Abuse Rules

The following rules apply whenever working on Google Cloud ephemeral cloud sandboxes:

- **NEVER grant `roles/owner` or `roles/editor`** to `user_0` in `sandbox.yaml` or Terraform.
- **NEVER grant `roles/iam.serviceAccountAdmin` or `roles/iam.serviceAccountUser` at project level**. Scope to specific `google_service_account` resources in Terraform via `google_service_account_iam_member`.
- **NEVER pair Managed Web IDE Proxy (`ide`, `cloud_terminal`, `looker_instance`, `jupyter_notebook`) with `policy_tier: genai_sandbox`**: Managed Web IDE Proxy (`ide-provisioner@`) is exempted from the `genai_sandbox` IAM Deny policy (`Policy-Deny-SA-Keys`) and injects `/home/user/keys.json` with project-wide permissions into a GKE container in `sandbox-platform-prod`, enabling full LLM API key exfiltration (`SEC-001`).
- **NEVER mint a `google_service_account_key` on an SA with `roles/aiplatform.user`, `roles/editor`, or `roles/owner`**: `tf/secure_network.tf` (VPC egress firewall) ONLY protects **VM-attached service accounts** (where tokens remain inside the student VPC via IMDSv2 `169.254.169.254`). Once an exportable JSON key (`google_service_account_key` or `/home/user/keys.json`) is copied out of the browser, attackers invoke `https://aiplatform.googleapis.com` over the public internet (Control Plane), bypassing `tf/secure_network.tf` 100%. If a `google_service_account_key` is required, it must be scoped strictly to non-LLM roles (e.g., `roles/storage.objectViewer`) + IAM time-expiry conditions.
- **`roles/resourcemanager.projectIamAdmin` is strictly development-only** and MUST be removed from `sandbox.yaml` before any Pull Request is opened or merged.
- **All hardened labs MUST restrict outbound egress** to HTTP (80), HTTPS (443), DNS (53), and NTP (123) in `tf/secure_network.tf`.
- **Pre-Merge Validation is Mandatory**: Every lab modification must pass `validate_pre_merge` before submitting a PR.
- **QA Decoupling**: Never treat pre-existing baseline lab functional bugs as security regressions. Verify against untouched baseline.
- **Strict Ticketing & PR Guardrail**: Do NOT open GitHub PRs or file GitHub Issues tickets autonomously unless the user explicitly requests a "rollout", "QA testing", or batch PR operation.
- **Keep Milestone Ticket `SEC-100` De-Cluttered**: **NEVER post batch PR tables, staging `/execute-lab` test logs, Activity Tracking check rollups, or granular lab-level comments to `SEC-100` (`[Project Phase] Apply Hardening to all sandboxes`)**. `SEC-100` is an executive Milestone ticket reported by management for tracking high-level project phase milestones only. Post detailed test logs and PR links ONLY on the individual per-lab child tickets (or a dedicated operational QA parent ticket), and only update `SEC-100` for major milestones when explicitly instructed by the user.
- **Feature Branch & PR Hygiene for `cloud-sandbox-security` / `harden-sandbox` Updates**: Whenever updating the `cloud-sandbox-security` plugin (`engine.py`, `kb/`, `rules/`) or the `harden-sandbox` skill in `zachnoah89/agentic`, you MUST first run `git fetch origin main`, verify whether prior feature branches/PRs have already been merged, and create a **brand-new feature branch** (`feat/<slug>`) branched cleanly off `origin/main` (preferring an isolated `git worktree` if concurrent tasks are running). NEVER commit or push directly to `main` or onto an already-merged PR branch.
- **Mandatory `runtime.yaml` on all Terraform startup scripts**: Whenever creating or configuring a Terraform harness (`path: tf` or `terraform/`) wired to `startup_script` in `sandbox.yaml`, you MUST ensure `runtime.yaml` (`runtime: terraform`, `version: 1.12.1`) is present in that directory. Missing `runtime.yaml` causes the Cloud Sandbox Platform script runner to reject the bundle at launch: 'bad request, invalid script: missing runtime.yaml file' (SEC-004).
